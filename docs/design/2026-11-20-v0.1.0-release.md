# v0.1.0 released — 2026-11-20

What was checked: the maintainer's part of stage plan 0003 T6, the first
release. The CHANGELOG section was renamed to `[0.1.0] - 2026-11-20`, the
commit was tagged `v0.1.0` (annotated) by the agent at the maintainer's
request, and the maintainer pushed and started the release workflow.

## Before the tag

- `govulncheck ./...` with Go 1.26.8 found 11 standard-library
  vulnerabilities that the code can reach (net/http, crypto/x509,
  crypto/tls, net/textproto), all fixed in Go 1.26.11. The pin in
  `.mise.toml` was raised to 1.26.11 (commit `0e6e5bc`). With it,
  `govulncheck` finds no reachable vulnerability; one in a module the code
  does not call remains (GO-2026-5024, `golang.org/x/sys` v0.41.0, fixed in
  v0.44.0).
- The release workflow now runs `govulncheck` after `make verify` (ADR-0020,
  commit `6b9e9e3`).

## Release workflow

| Run | Result | Cause |
|---|---|---|
| 44743406264 | Failed at "Build the release archives", exit 126 | `scripts/release-build.sh` was committed without the executable bit and the workflow ran it directly; `make dist` runs it with `bash`, so the local check of 2026-11-19 did not see it |
| 44743983037 | Pass, all steps, 1 m 54 s | Workflow from `main` at `4bf7796`, which runs both release scripts with `bash` |

The tag was to move to `4bf7796` before the second run, but it was not
moved: `v0.1.0` points to `6b9e9e3`, as the first run had it. A workflow
started by hand takes its steps from the branch it is started on (`main`)
and checks out the tag's files, so the second run built `6b9e9e3` with the
fixed steps. `6b9e9e3` and `4bf7796` differ only in the workflow file and two
file modes, so the binaries are the same as from `4bf7796`. The tag stays
where it is, so that it matches the published release.
